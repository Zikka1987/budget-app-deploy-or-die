# Project Decisions

## Architecture
- Supabase is the shared backend (Postgres hosting, Auth, Storage)
- FastAPI is the deterministic business-logic layer
- Direct asyncpg for all DB reads/writes; Supabase client only for Auth + Storage
- Multi-step financial writes use real DB transactions (BEGIN/COMMIT/ROLLBACK)
- Python owns all rule-heavy logic
- AI only helps with receipt interpretation and categorization
- AI providers are behind an abstract interface (ai/base.py); Anthropic is first provider

## Data Safety
- All receipt-derived transactions require user review before posting
- Receipt confirmation and savings posting are idempotent (idempotency_key on transaction_groups)
- Savings proposals are idempotent (UNIQUE on rule_id + month)
- Categories use stable UUIDs; renaming creates aliases, never changes ID
- Soft-delete for categories (archived_at)

## Budget
- Calendar months (1st to last day), no fiscal_day
- Late-income shift: optional rule where income after cutoff day counts toward next month
- Month creation copies previous month's structure and planned amounts (idempotent)

## Savings
- Two automatable rule types: percent_of_income, fixed_monthly
- Manual savings is a direct transaction flow, not a rule type
- Proposals generated by Python, reviewed by user, posted after approval

## Household
- One household per user (enforced at DB level, v1 constraint)
- 2 users per household
- RLS on all tables via get_household_id() helper

## Other
- Currency: DKK only
- Receipt language: Danish
- Amounts always positive; transaction_type indicates direction
- transaction_source enum tracks origin of every transaction
